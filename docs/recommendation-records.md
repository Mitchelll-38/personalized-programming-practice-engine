# Recommendation snapshot records

Owner: coordinator. Purpose: retain which candidates, predictions and policy/model
versions produced a recommendation before separately recording choices/outcomes.
Dependencies: existing local SQLite connection boundary. Acceptance: strict finite
candidate values, preserved rank order, synthetic-only metadata, append-only
storage, idempotent additive schema and unchanged existing interactions.

`record_snapshot` accepts a validated `RecommendationSnapshot` and assigns a UUID
and UTC timestamp. It stores candidate order, model/policy/dataset versions,
calibration declaration and the history sequence position used by the caller.
Only the local `demo` learner and declared synthetic data are supported. Candidate
IDs must be distinct; probability and score values must be finite. Scores need
not be probabilities. No code, future outcome or selected-exercise field exists.

An additive `recommendation_snapshots` table uses the existing private SQLite
connection. Existing interaction rows and attempt numbers are untouched. Repeated
calls create distinct records; timestamps/IDs are generated by the storage boundary,
not supplied by a client. `get_snapshot` and bounded `list_snapshots` reconstruct
strict records on read. There is no update/delete operation; the application is
append-only, but the local database is not a tamper-evident audit system.

The caller is responsible for truthful model/policy/history metadata. A generated
snapshot does not prove the UI displayed it or that a learner selected it. Selection
and attempt links will be separate events; do not infer exposure, learning gains
or recommendation effectiveness from these records.

This PR adds storage only. No API route starts logging or exposes the records yet;
ranking, manual outcomes, frontend behavior and existing persistence stay unchanged.
Tests use original synthetic candidates and private temporary databases. Keep real
row-level data and databases out of public Git.


## API generation integration plan

Owner: coordinator. Dependency: snapshot storage PR #41. Purpose: bind each
recommendation response to the exact generated candidate ranking and observed
history position, without inferring a learner saw or selected it. Acceptance:
read history once, rank once, persist those exact ordered scores with current
model/policy/dataset versions, return its server snapshot ID and history position,
and preserve previous ranking/replay behavior. Each request creates a distinct
generation record. Persistence failure must fail the request rather than return
an unrecorded snapshot identity. Choice/outcome linkage and UI events are separate
PRs. GET now records generation as a local demo audit side effect; it is not an
exposure counter and automatic retries can create additional records.
